# ODH Foundation — Website Backend

The content management backend for [odhfoundation.org](https://odhfoundation.org), built with
**Payload CMS 3** embedded in **Next.js 16**, backed by **PostgreSQL**.

ODH Foundation is an Indian NGO — the philanthropic arm of ODH Group, founded in 2023 — working in
health, education, environment and livelihood across Uttar Pradesh. This repository is a ground-up
rebuild of their website.

## What this does

| | |
|---|---|
| **Admin panel** | `/admin` — a full CMS for non-technical staff. Generated by Payload from the collection configs. |
| **REST API** | `/api/*` — auto-generated. No API code was written for content. |
| **GraphQL** | `/api/graphql` — available, unused. |
| **Content model** | 12 collections, 3 globals, 11 page-builder blocks |
| **Page builder** | Editors compose pages by dragging blocks. Section order lives in the database, not in code. |
| **Uploads** | Photos (auto WebP + 4 responsive sizes), Graphics (logos/icons, unmodified), Documents (PDFs) |
| **Roles** | `super-admin` · `editor` · `finance` |

## Setup

### 1. Clone and install

```bash
git clone https://github.com/sonamsrivastava458/odh-foundation-web.git
cd odh-foundation-web
pnpm install
```

### 2. Create the database

```bash
createdb odh-foundation-web
```

Or with psql:

```powershell
$env:PGPASSWORD='<your-postgres-password>'
& 'C:\Program Files\PostgreSQL\17\bin\psql.exe' -U postgres -h 127.0.0.1 -c "CREATE DATABASE \"odh-foundation-web\";"
```

### 3. Configure the environment

```bash
cp .env.example .env
```

Then edit `.env`:

```bash
DATABASE_URL=postgres://postgres:<password>@127.0.0.1:5432/odh-foundation-web
PAYLOAD_SECRET=<a 32+ character random string>
NEXT_PUBLIC_SITE_URL=http://localhost:3000
```

Generate a secret:

```powershell
$bytes = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes)
($bytes | ForEach-Object { $_.ToString('x2') }) -join ''
```

`PAYLOAD_SECRET` signs the authentication JWTs. Changing it logs everyone out (it does not invalidate
passwords — those are hashed per user).

> **`.env` must never be committed.** It is git-ignored. Verify with `git check-ignore -v .env` —
> it should print a `.gitignore` line. If it prints nothing, **stop**.

### 4. Run

```bash
pnpm dev
```

Open **http://localhost:3000/admin**. Payload will prompt you to create the first admin user.

> **After creating that user, give yourself the `super-admin` role** (Users → your user → Roles), then
> **log out and log back in**. The role is stored in the auth cookie, so an old cookie still says "no
> roles".

## Why local Postgres and not Neon?

The spec calls for Neon (serverless Postgres). We develop against **local** Postgres and reserve Neon
for production.

The Neon project was created in `us-east-1` (USA). Payload pushes its schema on every dev-server boot,
which runs dozens of queries — and from India that link timed out reliably:

```
Error: cannot connect to Postgres.
  connect ETIMEDOUT 18.215.6.120:5432
```

Local Postgres in development, Neon in production, is standard practice. Only `DATABASE_URL` changes.

> **When creating the production Neon project, choose a Mumbai or Singapore region** — not `us-east-1`.
> The latency that made development unworkable will also hurt production TTFB.

```bash
pnpm build            # production build
pnpm start            # serve the production build

pnpm generate:types   # regenerate src/payload-types.ts — run after ANY field change
npx tsc --noEmit      # typecheck

pnpm test             # ⚠️ no tests written yet
pnpm lint             # ⚠️ currently broken — see ROADMAP.md §19.2
```

### The one thing that will waste your afternoon

**Payload creates database tables at boot, not on hot-reload.**

Add a field → hot-reload updates the code → the database has no column for it → you get
`relation "x" does not exist`.

**Restart the dev server after any schema change.** Every time.

## For the frontend developer

Three things that will otherwise cost you a day:

1. **The homepage needs `depth=3`.**
   ```
   GET /api/pages?where[slug][equals]=home&depth=3
   ```
   At the default depth, `ctaBand.qrImage` comes back as a **number**, not an object. This fails
   **silently** — no error, the QR code simply does not render.

2. **Photos have `sizes`. Graphics do not.**
   `graphic.sizes.card.url` throws. Graphics (logos, icons, QR codes) are stored unmodified — use
   `graphic.url`. Photo sizes can each be `null` (we never upscale), so fall back:
   `photo.sizes.hero?.url ?? photo.sizes.feature?.url ?? photo.url`

3. **Do not fetch projects or campaigns separately for the homepage.**
   Reference blocks arrive with an **`items`** array already filled with the full documents. One
   request returns the entire homepage.

Also: **never hardcode the section order.** Map over `page.layout` and switch on `blockType`. The
order lives in the database because the editor owns it. Render `null` for an unknown `blockType` —
a new block in the CMS must not take the site down.
